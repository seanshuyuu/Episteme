# 业务实体与规则

## 1. 领域边界

Episteme 管理用户、工作空间、访问授权与配置。每个工作空间对应一个独立 Git 仓库；目录和文件正文以仓库中的 Git tree / blob 为准。数据库不复制正文，也不维护一份可与 Git 冲突的目录树。

```text
身份与授权：PostgreSQL（Identity + OpenIddict + Episteme 元数据）
内容与版本：工作空间目录中的 Git 仓库（目录、文档正文、提交历史）
```

Git 是文档内容和目录结构的唯一事实来源。目录由仓库中文件路径推导；空目录通过仓库内的占位文件（例如 `.gitkeep`）纳入 Git。若后续需要全文搜索或高性能筛选，可增加可重建的索引/投影，不改变 Git 为事实来源的原则。

## 2. 实体

### 2.1 身份与 token

| 实体 | 关键字段/关系 | 说明 |
|---|---|---|
| `ApplicationUser` | `Id: Guid`、用户名、邮箱、状态、创建时间 | 继承 ASP.NET Core Identity 用户；用户停用优先于物理删除。 |
| `IdentityRole<Guid>` / `UserRole` | Identity 标准角色及用户角色关联 | 系统级角色，例如 `Administrator`、`User`；仅系统级角色，不替代工作空间成员授权。 |
| `UserWorkspaceSettings` | `UserId`（唯一 FK）、默认工作目录相对路径、偏好设置 | 用户的逻辑工作目录限定在服务端配置的用户沙箱下；不保存或接受任意服务器绝对路径。 |
| OpenIddict 持久化实体 | Application、Authorization、Scope、Token | 使用 OpenIddict EF Core store 管理客户端、授权、scope、访问/刷新 token 和撤销；不自建 token 表或签发逻辑。 |

### 2.2 工作空间与访问控制

| 实体 | 关键字段/关系 | 说明 |
|---|---|---|
| `Workspace` | `Id: Guid`、`CreatedByUserId`、名称、slug、类型、描述、配置 JSON、默认分支、不可变 `StorageKey`、状态、时间戳、并发戳 | `StorageKey` 由服务端生成并用于定位仓库；物理位置由部署级存储根目录 + StorageKey 计算。`Configuration` 映射 PostgreSQL `jsonb`，带 schema version。并发戳由应用在更新时轮换，用于 EF Core 乐观并发检查。 |
| `WorkspaceMember` | `WorkspaceId`、`UserId`、角色、状态、加入时间、邀请/添加者 | 唯一约束 `(WorkspaceId, UserId)`；创建者同时成为首位 Owner。支持以后分享工作空间，但 MVP 可只开放所有者管理。 |
| `WorkspaceRole`（值对象/枚举） | `Owner`、`Editor`、`Reader` | 固定工作空间角色，不在 MVP 提供用户自定义角色管理。权限由 ASP.NET Core Authorization policy/handler 实现。 |
| `AuditEvent` | `Id`、操作者、可选工作空间、事件类型、时间、非敏感 JSONB 摘要 | 记录账户、授权、工作空间设置等管理事件。文档内容变更以 Git commit 为权威历史，不重复存入审计表。 |

### 2.3 项目层

| 实体 | 关键字段/关系 | 说明 |
|---|---|---|
| `Project` | `Id`、`WorkspaceId`、创建者、名称、slug、描述、独立 `StorageKey`、默认分支、状态、并发戳、时间戳 | 工作空间下的独立 Git 项目。每个项目拥有独立仓库、目录树、README 和提交历史，不把项目文件直接混入工作空间层。 |
| `ProjectStatus` | `Working`、`Archived`、`Discarded` | 项目状态。删除采用软删除：标记为 `Discarded`，保留仓库与审计；归档不允许常规写入但保留仓库。 |

迁移兼容：升级前的每个工作空间会创建一个默认 `Project`，其 `Id` 和 `StorageKey`沿用原工作空间的仓库身份，确保现有目录、文档和历史不会丢失。后续新项目使用独立 `StorageKey`。

项目可由文件夹升级或降级：

- **文件夹升级为项目**：复制源项目中的目录及文件到独立项目仓库，保留源目录作为安全副本；新项目自动生成描述和 slug，并要求工作空间级管理权限。
- **项目降级为工作空间目录**：将项目仓库内容复制到工作空间默认项目的以项目 slug 命名的目录，再将原项目归档；原项目仓库不删除，保留恢复/审计能力。
- **批量移动**：目录树支持多选文件和文件夹，一次操作按依赖顺序移动到目标目录；整个操作基于当前 Git HEAD，并对冲突和非法目标逐项明确失败。

### 2.3 Git 内容模型（非 EF Core 实体）

以下概念由 Git 仓库直接表达，不另建 PostgreSQL 表：

- **目录**：Git tree 中的路径；文件系统查询结果不持久化为另一份目录实体。
- **文档/文件**：相对路径对应的 Git blob；可由 API/MCP 按需读取。
- **版本**：Git commit；提交 ID 是稳定版本标识。
- **工作分支**：MVP 仅有工作空间的默认分支，所有写操作由服务端在仓库锁内顺序提交。分支/合并流程留待后续决定。

一次文档写操作应验证工作空间权限和相对路径，取得工作空间级写锁，检测调用方基于的 HEAD（若提供），然后执行文件操作并提交 Git。并发版本不匹配返回冲突，而不静默覆盖。写操作和审计应明确区分：Git commit 中记录操作者标识和变更摘要；数据库 `AuditEvent` 不保存正文。

## 3. 工作空间类型与配置

建议内置类型：`Code`、`Skill`、`Research`、`BusinessNovel`、`Custom`。类型代表模板/默认行为，不限定工作空间能存放的文件类型。类型专属设置放在有版本号的 JSON 配置中，避免为每类空间创建一组互相重复的表。模板可提供初始目录骨架，用户仍可调整目录。

工作空间配置导入/导出建议采用版本化 JSON 清单，例如 `episteme.workspace.json`，字段包含格式版本、空间名称/类型、非敏感设置和可选的初始目录骨架。导入必须验证 schema、名称、路径及受支持的配置版本，并按普通创建流程重新做授权。默认不导入成员角色、token、正文或 Git 历史；导出配置也不等同于内容备份。

## 4. 角色和权限矩阵（提案）

| 能力 | 系统 Administrator | Owner | Editor | Reader |
|---|---:|---:|---:|---:|
| 查看工作空间、目录和文档 | 是 | 是 | 是 | 是 |
| 创建/修改文档、目录并提交版本 | 是 | 是 | 是 | 否 |
| 查看文档版本、恢复到旧版本（生成新提交） | 是 | 是 | 是 | 否 |
| 修改工作空间名称、类型和配置 | 是 | 是 | 否 | 否 |
| 成员管理、转移 Owner、归档/删除空间 | 是 | 是（至少留一名 Owner） | 否 | 否 |
| 管理系统用户、全局角色和他人 token | 是 | 否 | 否 | 否 |
| 查看/撤销本人 token 或授权会话 | 是 | 是 | 是 | 是 |

工作空间资源每次访问都须验证调用主体的系统身份和该空间的成员角色；MCP 工具与 Web API 共用同一授权策略。MCP 客户端传入的 workspace ID 不能代替授权检查。

## 5. 删除、路径与一致性约束

- 工作空间删除默认采用软删除/归档；彻底清除仓库是独立的、有保留期和确认保护的后台操作。
- 禁止 `..`、绝对路径、符号链接逃逸、仓库元数据路径及规范化后越过工作空间根目录的路径；路径大小写和 Unicode 规范化策略在实现前确定。
- 目录移动/重命名是仓库文件路径批量变更并作为一个 Git commit；非空目录删除须明确删除其子文件，工具响应不可模糊成功。
- Git 操作、文件系统和 PostgreSQL 事务之间不能组成单一 ACID 事务。仓库写入要以工作空间锁串行化；失败应显式返回错误并可从 Git 状态/提交历史恢复，不可返回成功形状的默认结果。
- 数据库不直接删除 Identity 用户；用户停用、工作空间归档及数据保留策略须先处理关联和审计记录。
