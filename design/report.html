01执行摘要

Episteme 以“工作空间”为核心：用户可按代码、Skill、论文研究、商业小说等场景创建不同空间； 每个空间拥有独立 Git 仓库，目录、文档正文和版本历史由 Git 管理。

内容与版本

Git 是唯一事实来源

文档正文、目录树、版本历史落在空间仓库，不在数据库重复存储。

身份与元数据

PostgreSQL + EF Core

持久化用户、空间、成员授权、用户偏好和管理审计。

统一业务能力

Web API + MCP

两个入口共享 Application 用例、校验和授权策略。

方案状态：用户已确认当前方案，后端正在分阶段实现。本文记录设计基线； 实际完成范围和验证结果见 后端实现与验证进展。

02核心设计原则

明确数据边界

PostgreSQL 保存身份和管理元数据；Git 保存内容与版本。避免两份目录/正文数据相互冲突。

按空间隔离授权

系统角色与空间成员角色分离；每次 API/MCP 请求均校验用户、scope 和空间权限。

不开放任意服务器路径

工作目录采用沙箱内逻辑相对路径；API/MCP 不接受服务器绝对路径。

优先成熟组件

使用 Identity、OpenIddict、EF Core、Npgsql、Refit、官方 MCP SDK 和 Git，不自建基础协议。

配置导入/导出 ≠ 内容备份： 默认配置清单只保存空间配置与可选目录骨架，不包含正文、token、成员权限或 Git 历史。

前后端分离：前端通过 Web API 消费服务；MCP Client 连接独立 MCP Server。 两个宿主都把请求交给同一 Application 层，不互相绕行调用。

04业务实体与数据归属

数据库实体（PostgreSQL）

ApplicationUser

  • Identity 用户（Guid 主键）
  • 用户名、邮箱、状态、创建时间
  • 停用优先于物理删除

IdentityRole / UserRole

  • 系统级 Administrator / User
  • 使用 Identity 标准角色机制
  • 不替代空间成员授权

OpenIddict 持久化实体

  • Application、Authorization、Scope、Token
  • 管理签发、刷新、撤销及授权会话
  • 使用官方 EF Core Store

UserWorkspaceSettings

  • UserId 唯一外键
  • 默认工作目录相对路径
  • 用户偏好 JSON

Workspace

  • 名称、slug、类型、描述、状态
  • 服务端生成且不变的 StorageKey
  • 版本化 jsonb 配置、默认分支
  • 并发戳、创建/更新时间

WorkspaceMember

  • WorkspaceId + UserId 唯一
  • Owner / Editor / Reader
  • 成员状态、加入时间、添加者

AuditEvent

  • 操作者、可选空间、事件类型、时间
  • 只保存非敏感 JSONB 摘要
  • 不重复保存文档正文历史

Git Tree（非 EF 实体）

  • 工作空间目录结构与文件路径
  • 空目录以占位文件纳入 Git
  • 不在数据库复制目录树

Git Blob / Commit（非 EF 实体）

  • Blob 保存文档正文
  • Commit 是版本历史与稳定版本标识
  • 恢复旧版本产生新提交
工作空间类型：Code、Skill、Research、 BusinessNovel、Custom。类型提供模板/默认行为，类型专属设置放在有 schema version 的 JSON 配置中。

用户与系统角色

  • ApplicationUser 1 — 0..1 UserWorkspaceSettings
  • ApplicationUser * — * IdentityRole
  • 由 Identity UserRole 关联

工作空间与成员

  • Workspace 1 — * WorkspaceMember
  • ApplicationUser 1 — * WorkspaceMember
  • 成员唯一键：(WorkspaceId, UserId)

审计与空间

  • ApplicationUser 0..1 — * AuditEvent
  • Workspace 0..1 — * AuditEvent
  • 空间归档/成员变更有管理审计
ApplicationUser ──创建──▶ Workspace  ·  Workspace ──授权成员──▶ WorkspaceMember  ·  Workspace ──StorageKey──▶ Git 仓库
关键约束：创建者关系只作创建审计；当前 Owner 以 WorkspaceMember.Role 为准， 且每个有效空间必须至少有一名 Owner。StorageKey 唯一且不可修改；用户/空间采用停用或归档语义，避免级联删除数据。

06授权模型

系统级角色控制平台管理能力；空间级角色控制具体空间内的资源。MCP 的 OAuth scope 与空间角色需同时通过。

能力AdministratorOwnerEditorReader
读取空间、目录、文档✓✓✓✓
写入文档/目录并提交版本✓✓✓—
查看历史、恢复版本（新提交）✓✓✓—
修改空间名称、类型和配置✓✓——
成员管理、转移 Owner、归档✓✓（保留一名 Owner）——
管理系统用户、全局角色、他人 token✓———
查看/撤销本人 token 或授权会话✓✓✓✓

初版采用固定 Owner / Editor / Reader，不开放用户自定义角色。创建者成为首位 Owner。

07MCP 与 Web API 能力

工作空间

list_workspaces · get_workspace · create_workspace · update_workspace · delete_workspace（默认归档）

目录

list_directory · create_directory · move_directory · delete_directory

文档

read_document · create_document · update_document · move_document · delete_document

版本与配置

get_document_history · restore_document_version · export_workspace_config · import_workspace_config

  • 认证主体来自受验证的 Token，不接受调用者传入的 user ID 冒充身份。
  • 所有工具复用 Application 层用例和权限检查，不直接访问 EF Core 或 Git。
  • 写请求校验角色、路径、输入大小和预期版本；查询有分页与响应大小限制。
  • OAuth scope 控制协议级能力，空间成员角色控制资源级能力，二者缺一不可。

09安全、路径与一致性

  • 仓库定位：部署级 WorkspaceStorageRoot + 服务端生成的不可变 StorageKey；工作空间名称和 slug 不作为物理路径。
  • 路径边界：拒绝绝对路径、..、符号链接逃逸、仓库元数据路径及越界规范化结果；先鉴权，再访问磁盘。
  • 并发写入：工作空间级写锁，检测预期 HEAD；不匹配返回冲突，不静默覆盖。恢复历史通过新提交完成。
  • 删除：工作空间默认归档；彻底清除仓库通过有保留期和确认保护的后台任务执行。
  • Token 与日志：短期 access token、refresh 轮换/撤销、最小 scope；日志和配置导出不包含密钥、token、密码或正文。
  • 事务边界：Git 与 PostgreSQL 无共享 ACID 事务；管理变更和内容提交各有权威记录，失败显式返回并支持恢复/对账。
  • 错误表达：权限拒绝、非法路径、版本冲突、存储失败等使用明确错误，禁止将失败伪装成空内容或成功。

10设计决策

下列默认值作为已确认的后端设计基线；仍未具体确定的事项需在实现前明确。

  1. 1部署与工作目录：多用户服务端；用户工作目录限定为用户沙箱下的逻辑相对路径。
  2. 2MCP 连接：独立 MCP 宿主、官方 C# SDK、OAuth 保护的 Streamable HTTP；stdio 需求待定。
  3. 3认证与 Token：Identity + OpenIddict，支持标准 OAuth/OIDC、refresh/revoke 和 MCP scopes。
  4. 4角色模型：系统 Administrator/User；空间 Owner/Editor/Reader 固定角色。
  5. 5Git 工作流：每空间独立仓库；初版默认分支、写操作顺序提交，不开放分支/合并。
  6. 6配置清单：只含非敏感设置和可选空目录骨架；正文、权限、Token、Git 历史另行管理。
  7. 7前端技术栈：目前不指定 UI 框架；独立前端通过 API/OpenAPI 集成。
  8. 8空间类型：Code、Skill、Research、BusinessNovel、Custom；类型专属配置使用版本化 JSON。
  9. 9保留策略：默认软删除/归档；彻底清理由有权限的后台任务按保留期执行。
变更方式：重大设计调整需取得用户确认后实施。
