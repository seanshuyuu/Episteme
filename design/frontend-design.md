# Episteme 前端业务原型与组件方案

## 1. 设计目标

- 非管理员用户登录后直接进入其默认工作空间，打开目录/文档开始工作，不增加单独的营销式仪表盘。
- 工作空间所有者可把空间共享给其他用户，并授予只读或读写权限；接收方在自己的空间列表中看到共享空间和所有者名称。
- 将空间配置、共享管理集中到“工作空间管理”，个人偏好和登录安全放在“设置”，从文档工作流中分离。
- 管理员用户列表应展示每个用户拥有（Owner）的工作空间数量。
- 本阶段仅设计可点击静态原型，不创建 Blazor/Razor 页面。

两套角色页面分别见[普通用户原型](./prototype.html)与[管理员原型](./prototype-admin.html)。原型中的名称、文件、提交、账号和统计数字均为示例数据，不代表线上记录。

## 2. 页面信息架构

| 导航区域 | 页面/入口 | 内容与操作 |
|---|---|---|
| 工作区 | 默认工作区 | 用户登录后的首页；直接打开默认空间目录和文档，支持空间切换、创建/导入入口。 |
| 工作区 | 全部空间 | 平铺和详细列表切换；展示路径、类型、状态、所有者与本人权限，并提供对应空间的管理入口。 |
| 工作区 | 文档版本 | 展示当前文档的 Git 历史、查看/恢复入口；恢复会产生新提交。 |
| 账户 | 设置 | 展示“偏好设置”和“登录与安全”。 |
| 管理员专属页面 | 管理总览、用户管理 | 显示系统级概览、用户状态、系统角色和该用户拥有的工作空间数量；不混入普通用户导航。 |

普通用户主界面不使用通用左侧导航栏：左侧为当前空间的文档目录，中间为文档，右侧直接显示当前文档的版本历史。宽屏下拖动面板边缘可调整宽度，向外压缩到阈值自动隐藏；边缘小按钮可随时隐藏或恢复，隐藏后正文区自动扩展。窄屏采用纵向排列，保留面板折叠按钮。空间管理和设置是独立页面，通过顶部账户菜单进入，不占据文档主界面。管理员使用独立原型页，仅呈现系统管理总览和用户管理；两份原型之间的链接只是评审时的角色切换，不代表产品中管理员可随意切换身份。

## 3. 共享与所有权规则

- 工作空间 Owner 可按用户名/邮箱选择其他用户，并赋予 `Reader`（只读）或 `Editor`（读写）；不允许把空间所有权隐式转移给 Editor。
- Reader 可以查看空间文档和历史，不能写入、移动、删除或恢复内容；Editor 可以读写和恢复；Owner 管理空间设置与成员。
- 所有者的自有空间列表显示“我拥有”；共享空间列表显示“与我共享”、所有者姓名和本人权限（只读/读写）。
- 文档归属于工作空间，内容所有权归工作空间所有者；共享成员获得的是访问权，不是文档所有权。UI 在共享空间和文档上下文均展示空间所有者。
- 后端仍须对每次请求验证成员关系与角色。前端隐藏/禁用操作只是 UX，不构成授权边界。

当前后端已有成员列表、添加/恢复成员、角色设置和移除接口，角色覆盖 Owner/Editor/Reader。成员 API 使用用户 ID；按用户名/邮箱搜索可共享对象的选择器还需关联用户目录查询能力。添加管理员列表中的 Owner 数量字段也需要后端管理查询增加聚合，现有用户列表没有空间数量字段。

## 4. 配置与版本语义

需要区分两种“版本”：

1. **项目与目录树**：进入工作空间后先显示项目卡片；打开项目后进入该项目独立 Git 仓库的目录树，默认打开根目录 README.md。项目卡片展示文件数、目录数、描述和状态。
2. **目录树与文档内容**：以项目 Git 仓库为事实来源。创建/移动/删除目录和文档写操作会形成提交；当前后端提供按文档路径查询历史、按历史提交读取或恢复文档。恢复会生成新提交，不改写历史。
2. **工作空间元数据设置**：名称、类型和配置更新携带 `ExpectedVersion`，后端使用 `ConcurrencyStamp` 检查并发冲突。它用于防止覆盖并发更新，不是可浏览/恢复的设置历史。当前没有元数据设置历史 UI/API。

因此，目录和文档内容有 Git 版本事实；空间名称/描述/类型等设置当前只有并发版本戳。原型中应避免把并发戳标成“版本 v7”或暗示可回滚设置。目录操作虽然产生 Git commit，但现有可查询历史端点按文档路径查询；若产品需要单独浏览整个空间的提交流或目录变更历史，需新增相应 API。

配置文件导入/导出是另一条流程：版本化 manifest 包含非敏感设置和可选空目录骨架，不包含正文、成员权限、token 或 Git 历史。

## 5. 新建与导入交互

- “新建空间”用明确的对话框/窗口呈现：空间名称、slug、类型、描述；选择 Custom 后显示必填的自定义类型名称，说明创建者成为 Owner，并初始化独立 Git 仓库。当前后端类型是固定枚举，Custom 本身没有额外名称字段；自定义名称及其查询、修改、导入导出需扩展契约和持久化。
- “导入配置”用独立对话框/窗口呈现：选择 JSON manifest、显示校验后的名称/类型/目录预览，再填写目标名称与 slug 并确认导入。
- 对话框需要取消/关闭、必填校验、重复 slug/格式不支持错误和提交中状态。
- 成功后进入新工作空间；新空间成为默认空间的操作在个人偏好/空间设置中选择，不暗示自动更改当前默认空间。

静态原型的两个窗口可从“全部空间”页打开；新建空间只在页面内添加示例，不初始化仓库或自动切换内容。文件内容、提交、用户等仍是示例数据。

## 6. 设置与用户默认入口

普通用户登录后默认进入设置中配置的默认工作空间。如果默认空间暂不可访问（已归档、初始化失败或成员已移除），应明确提示并引导其从“全部空间”选择其他空间，不显示成功形状的空文档。

“设置”页面集中管理：

- **偏好设置**：主题模式、强调色、显示密度、默认工作空间。
- **登录与安全**：修改密码、退出登录、本人 token/授权元数据及撤销。

空间信息和共享权限通过独立“工作空间管理”页面的具体空间操作维护；设置页不再重复展示这两个分类。

主题模式支持跟随系统、浅色、深色；可自定义强调色并恢复默认。原型只将主题保存到浏览器本地。现有 `UserWorkspaceSettings` API 仅读写默认工作目录；跨设备同步主题和默认空间偏好需补充 API 契约。

### 工作空间管理

- 支持平铺/详细列表切换、按名称或路径搜索、类型和访问关系筛选；显示类型、个人工作路径、所有者、本人角色、状态和 MCP 状态。初始化中或已归档的空间不可当作可用空间打开。
- 空间状态在平铺、详细列表及管理员空间清单中采用一致的颜色和文字：正常（Active）为绿色、初始化中（Provisioning）为琥珀色、已归档（Archived）为灰色；深浅主题分别保证可读性，不单独依赖颜色表达状态。
- Active 空间可导出非敏感配置 manifest；Owner 可维护名称、类型、自定义类型名称、描述、MCP 策略与个人路径，管理共享成员并归档。共享空间按权限显示所有者、本人角色；Reader/Editor 不显示 Owner 管理操作。具体操作仍须服务端逐次检查 scope、成员角色与状态。
- 此处“路径”设计为**当前用户在该空间中的默认工作目录**，是空间内相对路径，不暴露或修改服务器仓库物理路径。现有 `UserWorkspaceSettings` 按用户存储单个目录，非逐空间；若要按空间分别维护，需扩展模型及 API、校验目录与处理已删除目录。共享成员可维护自己的个人路径，不应由 Owner 代为修改。
- 空间级 MCP 开关是待实现策略，不是 OAuth scope 或成员角色的替代；关闭时阻止经 MCP 对该空间的访问，开启时仍须检查认证、scope、成员权限与空间状态。现有 MCP 工具复用应用服务授权，尚无空间级开关或相应持久化/强制执行；列表里的开关状态仅为原型示例。
- Owner 可选择指定用户赋予 Reader/Editor，调整权限或在确认后撤回；不可通过共享管理移除唯一 Owner。用户选择器和当前角色均为示例；正式系统应按用户 ID 提交，并处理用户不存在、权限变更冲突及撤回后的访问。
- 归档须确认，并说明空间不可继续访问、仓库不删除；若为默认空间需引导用户另选。原型仅在当前页面保留归档状态，不代表后端已具备已归档空间列表或恢复入口。
- 原型中的空间增删改、共享和 MCP 开关仅更新页面内存，刷新后重置；导出按钮只演示提示，不会生成 manifest 或调用 API。其他示例空间不伪装成可切换的真实内容。

## 7. 管理员页面

管理员用户列表除了账号、状态、系统角色、创建时间，还应展示“名下工作空间数”。该数建议定义为用户作为 Owner 的空间数量，排除仅共享给用户的空间；点击可打开该用户拥有的空间清单。现有 `UserAdministrationController` 返回用户资料但未包含空间数，因此该列需要后端聚合/查询支持。用户列表和详情仍按系统管理员授权，不向普通用户暴露。管理总览中的系统总量/初始化数量也是示意信息，正式实现需要对应的聚合查询能力。

## 8. Blazor 与组件库建议

**建议以 MudBlazor 作为候选基线进行验证**，避免自建通用管理组件。它提供导航布局、表格、表单校验、菜单、抽屉、对话框、提示和主题基础。Episteme 专属的工作空间文件树、Git 文档历史和权限呈现由业务组件封装。

| 方案 | 适用判断 |
|---|---|
| MudBlazor（首选候选） | 组件覆盖较完整、主题体系直接，适合作为本项目工作空间管理 UI 起步基座；正式采用前验证目标 .NET/Blazor hosting 模式、无障碍、移动端和编辑器集成。 |
| MASA Blazor（备选） | 可作为组件体系与设计风格备选；按同一页面清单验证覆盖度、维护活跃度和团队熟悉程度后再决定。 |
| 自建组件 | 用于文件树、版本历史和权限展示等领域 UI；不建议重造表格、表单、弹窗、导航或主题 Provider。 |

最终包版本与托管模式（Interactive Server / WebAssembly / Auto）尚未锁定，应在前端工程启动时依据认证流程、离线/延迟要求和部署约束确定。

## 9. 文档类型、检索与编辑

普通用户主界面支持按文件类型选择对应查看器/编辑器：

| 类型 | 建议交互 | 依赖/限制 |
|---|---|---|
| `.txt` | UTF-8 纯文本编辑，支持换行与自动保存/显式保存 | 当前内容服务已按 UTF-8 读写文本，单次写入有 1 MiB 限制；需处理非 UTF-8 和大文件错误。 |
| `.md` | Markdown 源码编辑 + 预览切换 | 复用纯文本能力；预览需选用受维护的 Markdown renderer，并对原始 HTML 做安全处理，避免 XSS。 |
| 源码文件 | Monaco 等代码编辑器提供语法高亮、行号、搜索、缩进和基础编辑 | 只做编辑器高亮为中等成本；接入 Roslyn/语言服务器、智能补全、诊断和多语言 LSP 是高成本，应另行立项。 |
| `.pdf` | PDF 阅读、页码/缩放、文本选区高亮和批注列表 | 建议 PDF.js 阅读。标注需独立存储，并绑定 PDF 的 Git commit/blob 版本、页码、坐标、引用文本和作者；PDF 更新后旧标注必须保留在旧版并提示重定位。原文件保持不变。 |
| `.doc` / `.docx` | 优先支持检索文本提取与只读预览；原文件下载 | 旧 `.doc` 二进制格式兼容更复杂。DOCX 结构化文本提取可行，但高保真分页、表格/图片/样式/批注及浏览器内编辑成本较高；首期不承诺在线编辑。 |

未配置查看器或编辑器的文件类型显示“暂不支持预览或编辑”，保留原文件下载，不尝试将二进制内容当作文本。已支持预览但不支持编辑的格式应明确显示只读状态，而不是归类为不可预览。

检索入口应覆盖当前工作空间内的文件名、路径和可提取文本，结果显示文件类型、路径、命中片段，并跳转到文档或 PDF 页/标注。MVP 可先实现文件名/路径检索；全文检索需为 Git 内容建立可重建索引，并定义对 PDF 的文本抽取/OCR、Office 文档抽取、索引更新和权限过滤。扫描索引结果时必须按当前用户的空间权限过滤，不能因共享搜索泄露未授权内容。

## 10. 下载与归档交互

- 文件的右键/更多菜单提供原文件下载，目录的右键/更多菜单提供 ZIP 下载；目录标题栏的下载按钮直接下载整个工作空间 ZIP，正文工具区不重复提供下载菜单。
- ZIP 只包含当前调用者有权读取的工作空间内文件；忽略仓库元数据和内部文件，规范化 entry path，拒绝路径穿越/符号链接逃逸。
- 下载入口显示所选范围、文件数量/大小估计、生成中状态和过期/失败提示；大 ZIP 采用流式响应或有授权/过期时间的临时下载，不把全部内容缓存在内存。
- 目录/空间压缩属于内容导出，与配置 manifest 导出不同；是否包含 Git 历史应明确，本原型默认只下载当前提交树中的文件，不含 `.git` 或历史。
- 下载仍须验证 Reader 可读权限；不得用可猜测的永久 URL 绕过授权。

### 工作目录操作

- 目录标题栏的“＋”展开新建文件夹、新建文档、上传文档和上传文件夹。选中文件夹时以该文件夹为目标；选中文档时以文档所在目录为目标；未选择时使用工作空间根目录。界面始终展示当前操作路径，并允许点击根目录重新选择。
- 新建文件夹输入名称。新建文档输入不含扩展名的名称，并从明确支持编辑的类型中选择；当前原型列出 Markdown、TXT、C#，确认时自动添加对应后缀。名称和同目录冲突须校验，不能将输入解释为路径。
- 上传文件夹保留相对目录结构，处理浏览器不支持、文件冲突、取消和上传失败；浏览器文件选择接口可能无法枚举空文件夹，须明确告知。静态原型只在临时目录树中显示所选名称，不读取、上传或保存文件。
- 支持将文件或文件夹拖至目标文件夹或根目录；文件和文件夹右键菜单提供移动、下载、删除，同时提供键盘和触屏可用的更多菜单。移动对话框可选择目标目录，拒绝自身/子目录、同名冲突和越界路径；删除文件夹须明确确认递归影响。实际移动/删除仍需服务端验证权限、路径和预期 HEAD，并处理并发冲突。
- 原型中的目录变更与编辑内容仅存在当前页面内，刷新后重置，不创建 Git 提交；正式实现需处理空目录的 Git 存储方式、提交语义及文件移动后的历史关联。

## 12. 页面状态与交互约定

- 列表覆盖加载、空结果、分页、请求失败和访问被拒绝。
- 文档保存显示保存中/成功/冲突/验证失败；冲突保留编辑内容，不自动覆盖。
- 删除、归档、成员移除、令牌撤销和历史恢复均需确认并说明影响范围。
- `Archived`、`Provisioning`、`Active` 与只读/读写状态用文字标签呈现，不只依赖颜色。
- 所有表单提供明确标签、校验错误和键盘可达操作；窄屏仍可完成主要流程。

## 13. 普通用户主界面布局

- 默认空间是普通用户登录后直接进入的工作界面，不展示仪表盘或业务主导航。
- 左栏展示空间目录树，支持展开目录和选择文档；右栏默认展示所选文档的提交历史。
- 中间区域打开和编辑文档，展示当前 HEAD、保存状态及正文工具区中的保存按钮；不支持编辑的文档禁用保存。
- 宽屏拖动边缘手柄调整左右栏宽度，压缩到阈值自动隐藏；小按钮可隐藏或恢复至折叠前宽度，手柄支持键盘方向键。两栏互不影响，隐藏后正文自适应扩展。
- 中等屏幕下历史栏移至正文下方，窄屏下三栏纵向排列；面板小按钮仍可折叠/恢复，不显示无法使用的横向拖动手柄。
- 工作空间管理和设置作为独立页面，通过顶部账户菜单进入；离开后提供返回默认工作区入口。

## 14. 原型边界

`prototype.html`（普通用户）与 `prototype-admin.html`（管理员）是两份纯静态 HTML/CSS/JavaScript 文件，包含各自的交互页面，不包含 Blazor、Razor、服务端请求或真实数据。普通用户原型中的类型切换、检索、PDF 标记模式、下载选项、目录栏/历史栏显隐与宽度、主题本地保存和页面切换仅用于演示，不会检索或生成真实文件；保存按钮也不会写入服务端。
